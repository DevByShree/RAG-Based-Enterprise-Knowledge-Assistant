The strategy ensures that testing activities are organized, efficient, and capable of detecting defects early. Key Components of a Testing Strategy 1. Test Planning o Defines scope, objectives, resources, schedule, and tools. o Identifies testing techniques and responsibilities. 2. Test Design o Creation of test cases, test scenarios, and test data. 3. Test Execution o Running test cases and identifying defects. 4. Levels of Testing in Strategy Software Testing is essential to verify an application is working properly or not. To achieve this, testing can be done through various stages of development from each component to all system. Those "stages", called Levels of Testing, help to make sure all components of system are working properly. Incremental Integration Testing Modules are integrated step by step and tested gradually. Incremental integration testing is a software testing approach where individual software modules, which have already passed unit testing, are systematically integrated one by one or in small groups and tested after each step. The primary goal is to verify the interactions and data flow between components and identify defects early in the development lifecycle, making them easier and less costly to fix. 2. Non-Incremental Integration Testing All modules are integrated at once, then tested. Non-incremental integration testing, also known as the "Big Bang" approach, is a software testing strategy where all or most developed modules are combined at once and the entire system is tested as a single entity. This method is contrasted with incremental testing, where modules are integrated and tested step-by-step. Characteristics  Integration Approach: All components are integrated simultaneously after individual unit testing is complete. --- Page 4 ---  Planning: Requires simpler planning as the entire testing process is done in one go.  Resource Efficiency: Can be more efficient in terms of initial setup and execution time compared to planning multiple incremental steps.  Issue Detection: Defects are often detected late in the development process, as testing only begins after the entire system is assembled. When to Use Non-Incremental Testing Non-incremental integration testing is typically used in specific circumstances:  Small Systems: It is practical for small projects with a limited number of modules where the complexity of incremental testing is unnecessary.  Tight Coupling: It can be necessary if components are highly interdependent and cannot operate independently of one another.  Strict Deadlines: It may be used when there are tight project deadlines, although this approach carries significant risk. Regression Testing Regression testing is a software quality assurance practice that re-runs functional and non- functional tests to ensure that code changes—such as bug fixes, software updates, or new features—do not adversely affect existing, previously working functionality. It is critical for maintaining stability during rapid, iterative development cycles, preventing new bugs from introducing "collateral damage" to the system. Key Aspects of Regression Testing  Purpose: To verify that modified code hasn't broken existing features and to maintain software stability . --- Page 12 ---  When to Perform: After code changes, bug fixes, software enhancements, configuration changes, or when integrating new modules.  Types of Testing: Often includes a mix of unit, functional, and integration tests, typically automated for efficiency.  Approaches: o Full Regression: Re-running all tests, often used for major releases. o Selective Regression: Choosing a subset of tests focused on areas impacted by code changes. o Risk-Based Regression: Prioritizing tests based on the likelihood of failure and business impact.  Automation: Crucial for speed, especially in Agile and CI/CD environments where manual testing cannot keep up.  Comparison: Unlike retesting, which checks if a specific bug is fixed, regression testing confirms that the fix didn't create new issues elsewhere. Common Examples  Verifying that adding a "forgot password" feature did not break the login functionality.  Ensuring an API update doesn't disrupt data integration with the frontend.  Checking if modifying the database schema causes issues in existing report generation 2.
