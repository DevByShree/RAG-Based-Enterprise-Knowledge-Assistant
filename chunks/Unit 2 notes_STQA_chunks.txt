--- Page 1 --- UNIT 2 Software Testing Strategies and Techniques  Types of Testing Techniques- Introduction to Black Box, White Box, Grey Box Software testing techniques are generally categorised based on whether the internal structure and implementation details of the software are known to the tester. The three primary types are Black Box, White Box, and Grey Box testing. Black Box Testing Introduction: Black Box testing is a testing methodology where the internal structure, design, and implementation of the item being tested are unknown to the tester. This method focuses on the functionality of the application based purely on the requirements and specifications. The tester interacts with the system's external interfaces by providing inputs and examining the outputs, without any knowledge of how the system processes those inputs internally. Key Characteristics:  Focus: Functionality and user experience.  Knowledge Required: None of the internal code or structure.  Perspective: End-user perspective. --- Page 2 --- Techniques & Examples:  Equivalence Partitioning: Dividing inputs into valid and invalid groups and selecting test cases from each.  Boundary Value Analysis: Testing values at the extreme ends of valid input ranges.  Decision Table Testing: Testing complex business rules represented in a table format. White Box Testing Introduction: White Box testing (also known as clear box, glass box, or structural testing) is a method of testing where the internal structure, design, and implementation details are known to the tester. This approach requires the tester to have programming skills to examine the code, internal paths, and infrastructure. The goal is to verify the internal workings of an application rather than just its functionality. Key Characteristics:  Focus: Code structure, internal logic, and implementation.  Knowledge Required: In-depth knowledge of source code.  Perspective: Developer perspective. --- Page 3 --- Techniques & Examples:  Statement Coverage: Ensuring every line of code is executed at least once.  Decision (Branch) Coverage: Ensuring every branch (e.g., if/else statements) is executed .  Path Testing: Testing all possible paths through a given function or procedure. Grey Box Testing Introduction: Grey Box testing is a strategy that combines elements of both black box and white box testing. In grey box testing, the tester has partial knowledge of the internal structure or access to design documents and the database, but does not have complete access to the source code . This approach allows for more targeted testing while still maintaining a degree of separation between the developer and the tester. Key Characteristics:  Focus: Functionality and internal structure, with limited information.  Knowledge Required: Partial knowledge (e.g., access to database schemas or design documents).  Perspective: Hybrid of end-user and developer. --- Page 4 --- Techniques & Examples:  Matrix Testing: Testing variables to ensure proper system performance.  Regression Testing: Testing the impact of new code changes on existing functionality using some structural knowledge.  Pattern Testing: Analyzing past software defects to identify potential current vulnerabilities. Black Box Testing Black box testing, also known as behavioral, functional, or specification-based testing, focuses entirely on the inputs and outputs of the software system.  Core Principle: The software is treated as an opaque "black box." The tester does not need programming skills or access to the source code; instead, they interact with the application's user interface and provide various inputs to observe if the outputs match expected results based on the documented requirements.  User-Centric Focus: This method ensures the software meets end-user expectations and real-world usage scenarios, identifying issues with functionality, usability, and performance from the customer's point of view.  Techniques: Common techniques used to design effective black box tests include: o Equivalence Partitioning: Dividing input data into valid and invalid classes and testing a representative value from each. o Boundary Value Analysis (BVA): Focusing on testing values at the edges of valid input ranges, --- Page 34 --- where errors are more likely to occur (e.g., for a valid range of 10-100, testing 9, 10, 100, and 101). o Decision Table Testing: Creating a table to test combinations of conditions and their corresponding actions, useful for complex business rules. o State Transition Testing: Validating that the system correctly transitions between different states based on specific inputs or events. o Error Guessing: Using a tester's experience and intuition to anticipate where defects might occur and designing test cases for those scenarios. Requirement-Based Testing Requirement-based testing is a foundational element and key focus area of the black box approach.  Definition: It is a testing process where test cases are derived directly from the software's functional and non-functional requirements and specifications documents.  Purpose: The primary goal is to guarantee that every documented feature and behavior outlined during the initial phases of the project has been implemented correctly and functions as expected. --- Page 35 ---  Process: o Understand Requirements: Testers thoroughly analyze the requirements or user stories to determine what the system should do. o Design Test Cases: Test scenarios are created that directly map to each specific requirement. o Ensure Traceability: Clear links are established between each test case and its corresponding requirement, allowing for easy tracking and ensuring all requirements are covered. o Execute and Validate: Tests are executed, and the actual results are compared against the expected outcomes specified in the requirements. In essence, requirement-based testing is how black box testing achieves its primary objective: ensuring the software meets the documented specifications and user needs.
