Test Planning: 
Introduction to Test Planning 
Test Planning is the first and most important phase of the software testing life cycle (STLC). 
It defines the overall strategy, scope, resources, schedule, and deliverables required to 
perform testing activities effectively. 
A well-prepared test plan acts as a master document that guides the entire testing process and 
ensures that testing is carried out in a systematic and controlled manner. 
 
Definition of Test Plan 
A Test Plan is a formal document that describes: 
 
The testing strategy 
 
The scope and objectives of testing 
 
Required resources and schedule 
 
Planned test deliverables 
It clearly states what will be tested, how it will be tested, who will test it, and when testing 
will be completed. 
 
Preparing a Test Plan 
Introduction 
Preparing a Test Plan is the most important activity in the Test Planning phase of the 
Software Testing Life Cycle (STLC). 
A test plan acts as a blueprint for all testing activities and ensures that testing is conducted in 
a systematic, controlled, and effective manner. 
The test plan is prepared before test execution and is usually created by the QA Lead or Test 
Manager. 
 
Definition 
A Test Plan is a formal document that describes the testing objectives, scope, approach, 
resources, schedule, risks, and deliverables for a software project. 
It answers the following questions: 
 
What will be tested? 
 
How will it be tested? 
 
Who will perform testing? 
 
When will testing be completed?

test Approach, 
Introduction 
A Test Approach is an important part of the Test Plan that defines how testing will be 
carried out for a software project. 
It provides a high-level description of the testing strategy, methods, techniques, tools, and 
resources to be used during the testing process. 
The test approach ensures that testing activities are consistent, systematic, and aligned with 
project objectives. 
 
Definition 
A Test Approach is a section of the test plan that describes the overall testing strategy, 
including: 
 
Testing levels 
 
Testing types 
 
Testing techniques 
 
Tools and environment 
 
Roles and responsibilities 
It explains how the testing objectives will be achieved. 


--- Page 6 ---

 
Objectives of Test Approach 
 
To define a clear testing strategy 
 
To select appropriate testing techniques 
 
To ensure effective test coverage 
 
To standardize testing activities 
 
To reduce testing risks 
 
Components of Test Approach 
 
1. Testing Levels 
Testing levels define at which stage testing is performed. 
a) Unit Testing 
 
Performed on individual modules 
 
Usually done by developers 
 
Focuses on internal logic 
b) Integration Testing 
 
Tests interaction between modules 
 
Identifies interface defects 
c) System Testing 
 
Tests the complete system 
 
Performed by test engineers 
d) Acceptance Testing 
 
Validates system against user requirements 
 
Performed by customers/end users 
 
2. Types of Testing 
Testing types describe what aspect of the software is tested. 
Functional Testing 
 
Verifies functionality against requirements 
 
Example: Login, registration 
Non-Functional Testing 
 
Tests performance, security, usability 
 
Example: Load testing, stress testing 
 
3. Testing Techniques 


--- Page 7 ---

Testing techniques define how test cases are designed. 
a) Black Box Testing 
 
No knowledge of internal code 
 
Focuses on input and output 
b) White Box Testing 
 
Requires knowledge of code structure 
 
Focuses on logic and paths 
c) Gray Box Testing 
 
Combination of black and white box testing 
 
4. Test Execution Strategy 
Defines how test cases will be executed. 
Includes: 
 
Manual testing 
 
Automated testing 
 
Regression testing 
 
Retesting after defect fixes 
 
5. Tools and Test Environment 
Testing Tools 
 
Manual testing tools 
 
Automation tools (Selenium, JUnit) 
Test Environment 
 
Hardware 
 
Software 
 
Operating system 
 
Browsers and databases 
 
6. Roles and Responsibilities 
Defines who performs which testing activity. 
Role 
Responsibility

Automation Engineer 
Automation scripting

criteria for Testing: 
Introduction 
Criteria for Testing define the conditions that must be satisfied before testing can begin 
and before testing can be completed. 
These criteria help in controlling, monitoring, and evaluating the testing process and ensure 
that testing activities are conducted in a systematic and measurable manner. 
Testing criteria are an important part of the Test Plan. 
 
Definition 
Testing Criteria are a set of predefined conditions that determine: 
 
When testing should start 
 
When testing should stop 
They ensure that testing is neither started prematurely nor stopped without achieving quality 
goals. 
 
Types of Testing Criteria 
There are two main types of testing criteria: 
1. Entry Criteria 
2. Exit Criteria 
 
1. Entry Criteria 
Definition: 
Entry Criteria are the conditions that must be met before test execution can begin. 
They ensure that the testing environment is ready and the input artifacts are complete and 
approved. 
 
Common Entry Criteria 
 
Software requirements are reviewed and approved 
 
Test plan and test cases are prepared and reviewed 
 
Test environment is set up and stable 
 
Test data is available 
 
Build is successfully installed 
 
Required tools are configured 
 
Importance of Entry Criteria 
 
Prevents waste of testing effort 
 
Reduces rework 


--- Page 10 ---

 
Ensures readiness for testing 
 
Improves testing efficiency 
 
Example: 
Testing should not start if: 
 
Requirements are incomplete 
 
Build is unstable 
 
Test environment is not ready 
 
2. Exit Criteria 
Definition: 
Exit Criteria are the conditions that must be satisfied to conclude testing activities. 
They help decide whether the software is ready for release or further testing is required. 
 
Common Exit Criteria 
 
All planned test cases are executed 
 
Critical and high-severity defects are fixed and verified 
 
Test coverage goals are achieved 
 
Regression testing is completed 
 
Test summary report is prepared 
 
Stakeholder approval is obtained 
 
Importance of Exit Criteria 
 
Ensures quality standards are met 
 
Avoids premature release 
 
Provides objective release decision 
 
Confirms completion of testing 
 
Example: 
Testing can be stopped when: 
 
95% test cases pass 
 
No critical defects remain open

Criteria for testing play a crucial role in managing the testing process. 
By clearly defining entry and exit criteria, organizations can ensure that testing starts at the 
right time and ends only when quality objectives are achieved, leading to reliable and high-
quality software products. 
 
 
Test Deliverables, 
Introduction 
Test Deliverables are the documents, reports, and outputs produced during various phases of 
the Software Testing Life Cycle (STLC). 
They provide evidence of testing activities, help in tracking progress, and support decision-
making regarding software quality and release readiness. 
Test deliverables are defined during the test planning phase and are submitted to stakeholders at 
different stages of testing. 


--- Page 12 ---

 
Definition 
Test Deliverables are the artifacts created as a result of testing activities that describe: 
 
What testing was planned 
 
How testing was executed 
 
What defects were found 
 
The final status of the software 
 
Objectives of Test Deliverables 
 
To document testing activities 
 
To ensure traceability between requirements and test cases 
 
To communicate testing progress and results 
 
To support audit and compliance 
 
To assist in release decisions 
 
Types of Test Deliverables 
Test deliverables are categorized based on testing phases. 
 
1. Test Planning Phase Deliverables 
a) Test Plan 
 
Describes testing scope, approach, resources, and schedule 
 
Acts as a master document for testing 
b) Test Strategy 
 
High-level approach to testing 
 
Defines testing types and standards 
 


--- Page 13 ---

2. Test Design Phase Deliverables 
a) Test Scenarios 
 
High-level test conditions 
 
Derived from requirements 
b) Test Cases 
 
Step-by-step procedures to test functionalities 
 
Include inputs, expected results, and execution status 
c) Test Data 
 
Input data used for executing test cases 
d) Requirements Traceability Matrix (RTM) 
 
Maps requirements to test cases 
 
Ensures full test coverage 
 
3. Test Execution Phase Deliverables 
a) Test Execution Report 
 
Status of executed test cases 
 
Pass/fail statistics 
b) Defect / Bug Report 
 
Details of identified defects 
 
Includes severity, priority, and status 
 
4. Test Closure Phase Deliverables 
a) Test Summary Report 
 
Overall summary of testing activities 
 
Defect metrics and test coverage

Confirms completion of testing

Test Case Specification. 
Introduction 
A Test Case Specification defines the detailed conditions and steps under which a software 
application is tested to verify that it meets specified requirements. 
It is one of the most important documents prepared during the test design phase of the Software 
Testing Life Cycle (STLC). 
Test case specification ensures that testing is systematic, repeatable, and measurable. 
 
Definition 
A Test Case is a documented set of inputs, execution conditions, and expected results 
developed to verify a particular requirement or functionality of a software system. 
Test Case Specification refers to the complete description and documentation of test cases in 
a standard format. 
 
Objectives of Test Case Specification 
 
To verify functional and non-functional requirements 
 
To ensure maximum test coverage 
 
To detect defects effectively 
 
To enable repeatable and consistent testing 
 
To support regression and automation testing 
 
When Test Cases are Prepared 
 
After requirements analysis 
 
During the test design phase 
 
Before test execution begins 


--- Page 16 ---

 
Components of Test Case Specification 
A standard test case specification contains the following fields: 
 
1. Test Case ID 
 
A unique identifier for each test case 
 
Helps in tracking and reporting 
Example: TC_Login_01 
 
2. Test Case Description 
 
Brief description of what is being tested 
 
Written in clear and simple language 
Example: Verify login with valid credentials 
 
3. Preconditions 
 
Conditions that must be true before executing the test case 
 
Example: User must be registered 
 
4. Test Steps 
 
Step-by-step instructions to execute the test 
 
Written in sequential order 
 
5. Test Data / Input 
 
Input values used during execution 


--- Page 17 ---

 
Can be valid or invalid data 
 
6. Expected Result 
 
Expected system behavior after executing test steps 
 
Used to decide pass or fail 
 
7. Actual Result 
 
Actual behavior observed during test execution 
 
8. Test Status 
 
Indicates result of execution 
 
Values: Pass / Fail / Blocked / Not Executed 
 
9. Remarks / Comments 
 
Additional observations or notes

Metrics and Measurement: Types of Metrics, Product 
1. Introduction to Metrics and Measurement 
In software testing, metrics and measurement are used to quantify quality, productivity, 
and effectiveness of the software product and the testing process. 
They help in monitoring progress, improving decision-making, and ensuring quality goals 
are met. 
 
2. Definition 
Measurement 
Measurement is the process of collecting quantitative data about software attributes such as 
size, defects, effort, and performance. 
Metric 
A metric is a quantitative measure used to evaluate: 
 
Software quality 
 
Testing effectiveness

 
Process efficiency 
 
3. Objectives of Metrics and Measurement 
 
To measure software quality objectively 
 
To track testing progress 
 
To identify problem areas 
 
To improve process efficiency 
 
To support management decisions 
 
4. Types of Metrics 
Software metrics are broadly classified into the following types: 
1. Product Metrics 
2. Process Metrics 
3. Project Metrics

Metrics and Process Metrics, Object oriented metrics in testing. 
1. Introduction 
In software testing, metrics and measurement are used to quantify the effectiveness, 
efficiency, and quality of testing activities and software products. 
Among different types of metrics, Process Metrics and Object-Oriented (OO) Metrics play 
a vital role in improving testing processes and software quality. 
 
2. Process Metrics 
 
Definition 
Process Metrics measure the effectiveness and efficiency of the software testing process. 
They focus on how well testing activities are performed, rather than on the software product 
itself. 
Process metrics help in: 
 
Monitoring testing progress 
 
Improving testing processes 
 
Reducing defects and cost 
 
Objectives of Process Metrics 
 
To evaluate testing efficiency 
 
To monitor test execution progress 
 
To improve defect detection capability 
 
To optimize testing effort and cost 


--- Page 31 ---

 
To support continuous process improvement 
 
Common Process Metrics 
 
1. Test Case Execution Rate 
Definition: 
Measures the number of test cases executed in a given time period. 
Formula: 
Test Case Execution Rate = 
Number of Test Cases Executed / Time 
Importance: 
 
Tracks testing progress 
 
Helps in schedule management 
 
2. Defect Removal Efficiency (DRE) 
Definition: 
Measures how effectively defects are detected and removed before software release. 
Formula: 
DRE = 
Defects Removed Before Release 
------------------------------- × 100 
Total Defects 
Importance: 
 
Indicates testing effectiveness 
 
Higher DRE = better quality 
 
3. Test Effort Variance 
Definition: 
Measures the difference between planned effort and actual effort. 
Formula: 
Effort Variance = 
Actual Effort − Planned Effort 
Importance: 
 
Helps in effort estimation 
 
Identifies process inefficiencies 
 


--- Page 32 ---

4. Defect Leakage 
Definition: 
Defects found in later phases that were missed in earlier phases. 
Importance: 
 
Indicates weakness in testing process 
 
5. Requirement Coverage 
Definition: 
Measures the percentage of requirements covered by test cases. 
Formula: 
Requirement Coverage (%) = 
Tested Requirements / Total Requirements × 100

Definition

Object-Oriented (OO) Metrics measure the quality, complexity, and maintainability of 
object-oriented software systems. 
They help testers identify complex, fault-prone classes and prioritize testing efforts. 
 
Objectives of OO Metrics 
 
To measure design complexity 
 
To identify error-prone classes 
 
To improve test planning and coverage 
 
To enhance maintainability 
 
Common Object-Oriented Metrics 
 
1. WMC (Weighted Methods per Class) 
Definition: 
Measures the complexity of a class by counting the number of methods. 
Interpretation: 
 
High WMC → High complexity → More testing required 
 
2. DIT (Depth of Inheritance Tree) 
Definition: 
Measures the depth of inheritance hierarchy of a class. 
Interpretation: 
 
Greater DIT → Increased complexity 
 
Inherited defects possible 
 
3. NOC (Number of Children) 
Definition: 
Measures the number of subclasses derived from a class. 
Interpretation: 
 
High NOC → Greater reuse but more testing needed 
 
4. CBO (Coupling Between Objects) 
Definition: 
Measures the degree of interdependence between classes. 
Interpretation: 
 
High CBO → Higher risk of defects 
 
More integration testing required 


--- Page 34 ---

 
5. LCOM (Lack of Cohesion of Methods) 
Definition: 
Measures how well the methods of a class are related. 
Interpretation: 
 
High LCOM → Poor cohesion → Low quality

where testing is continuous, iterative, and integrated throughout the software development 
life cycle (SDLC). 
Unlike traditional testing, Agile Testing starts from the beginning of the project and

Agile Testing ensures early defect detection, faster feedback, and high-quality software 
delivery.

Agile Testing is a testing approach in which testing activities are performed continuously 
along with development in short iterations, focusing on customer requirements, 
collaboration, and adaptability to change.

Difference between Traditional and Agile testing, 
1. Introduction 
Software testing approaches vary based on the software development model used. 
Traditional Testing follows a sequential development model (such as Waterfall), whereas 
Agile Testing follows an iterative and incremental model. 
Understanding the differences helps in selecting the right testing strategy for a project.

4. Responding to change over following a plan

There are 12 principles behind the Agile Manifesto: 
1. Customer satisfaction through early and continuous delivery 
o Deliver valuable software frequently to satisfy customer needs. 
2. Welcome changing requirements

Agile Testing Quadrants, 
Agile Testing Quadrants 
Agile Testing Quadrants, proposed by Brian Marick, provide a framework for testing in 
Agile projects. They help teams understand what to test, why, and how, balancing business 
and technical needs. 
The quadrants are usually visualized as two axes: 
 
Horizontal axis: Technology-facing vs Business-facing 
 
Vertical axis: Support the team vs Critique the product 
This results in four quadrants: 
 
Q1 – Technology-facing, Support the Team 
 
Purpose: Ensure the code works correctly; guide development. 
 
Focus: Automated tests, unit tests, component tests. 
 
Examples: 
o Unit testing (JUnit, NUnit) 
o Component/integration testing 
o Test-Driven Development (TDD) 
 
Key Question: “Does the code work as expected?” 
 
Q2 – Business-facing, Support the Team 
 
Purpose: Confirm that requirements are correctly implemented. 
 
Focus: Functional tests that guide development. 
 
Examples: 
o Functional tests 


--- Page 43 ---

o Story tests / Acceptance Test-Driven Development (ATDD) 
o Prototypes, simulations 
 
Key Question: “Does the product meet business expectations?” 
 
Q3 – Business-facing, Critique the Product 
 
Purpose: Evaluate the product from the user’s perspective; provide feedback for 
improvement. 
 
Focus: Exploratory testing, usability, and acceptance. 
 
Examples: 
o User acceptance testing (UAT) 
o Exploratory testing 
o Alpha/Beta testing 
 
Key Question: “Does the product satisfy the customer?” 
 
Q4 – Technology-facing, Critique the Product 
 
Purpose: Assess technical quality, performance, and security. 
 
Focus: Non-functional tests that critique the system. 
 
Examples: 
o Performance testing 
o Load and stress testing 
o Security testing 
o Scalability testing 
 
Key Question: “Is the product robust, reliable, and maintainable?”

Automated Tests. 
Automated Tests 
Automated testing is the process of using software tools to execute test cases automatically, compare 
actual results with expected results, and report outcomes. It reduces manual effort, increases accuracy, 
and allows frequent testing. 
 
Advantages of Automated Testing 
1. Faster Execution: Tests run much quicker than manual testing, especially repetitive ones. 
2. Reusability: Test scripts can be reused across multiple releases. 
3. Consistency: Eliminates human error and ensures consistent execution. 
4. Continuous Integration Support: Works well with CI/CD pipelines for Agile development. 
5. Regression Testing: Efficient for checking old functionality after changes. 
6. Cost-effective in Long Run: Though initial setup is expensive, it saves time and effort in the 
long term. 
 
Disadvantages of Automated Testing 
1. High Initial Cost: Setting up automation tools and scripts can be expensive. 
2. Maintenance Overhead: Test scripts must be updated with changes in the application. 
3. Not Suitable for UI Changes: Frequent UI updates can break automated scripts. 
4. Requires Skilled Resources: Test automation needs programming knowledge. 
 
Types of Automated Tests 
1. Unit Testing 
o 
Tests individual components or functions of the software. 
o 
Example tools: JUnit, NUnit, TestNG 
2. Integration Testing 
o 
Tests interaction between different modules or services. 
o 
Example tools: JUnit, Postman (API testing), SoapUI 
3. Functional/UI Testing 
o 
Validates software behavior against requirements. 
o 
Example tools: Selenium, Cypress, QTP/UFT 
4. Regression Testing 
o 
Ensures that new changes do not break existing functionality. 
o 
Example tools: Selenium, TestComplete 
5. Performance Testing 
o 
Measures speed, scalability, and reliability. 
o 
Example tools: JMeter, LoadRunner 
6. Security Testing 
o 
Detects vulnerabilities and ensures protection against threats. 
o 
Example tools: OWASP ZAP, Burp Suite
